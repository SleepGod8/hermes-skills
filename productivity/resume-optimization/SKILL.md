# 简历优化（AI 工程化机制描述）

把平庸的"功能描述"转化为高价值的"AI 工程化机制描述"，直接返回结构完整、排版精美的简历项目模块内容。用户是求职者，此任务会反复出现。

## 触发条件

用户要求：优化/重构/润色简历项目内容、把功能描述改写成 AI 工程化描述、生成简历 Word 文档、参考某份简历编写自己的简历。

## 绝对红线（违反即失败）

- **禁止结果导向词汇**：全文严禁出现"实现了、解决了、提升了、确保了、优化了、达成了"等。
- **禁止无依据量化**：严禁编造或使用无法论证来源的具体数值（如"提升30%"、"降低50ms"）。
- **禁止括号解释**：严禁用括号对技术名词或流程做解释说明。
- **禁止引号引用**：严禁用引号描述数据流向或流程，必须用流畅文字。
- **禁止纯功能堆砌**：不要罗列 API 或基础功能，必须体现背后的 AI 逻辑。

## 项目背景/介绍规则

- **商业逻辑前置**：一句话点明项目存在的必要性与商业价值（如"解决长尾知识检索幻觉"、"降低多轮对话上下文成本"）。
- **去功能化**：不写"我们做了一个聊天机器人"，写"构建基于 AgenticRAG 的复杂意图分发与知识检索链路"。

## 核心职责规则

- **数量与篇幅**：4-6 条，每条高度概括（架构/体系级），300 字以内。
- **AI 强相关**：每条必须含 AI 核心环节，禁止纯后端/纯前端/纯运维描述。
- **技术栈锚点**：自然融入以下至少 2-3 个（不可生硬堆砌）：
  GraphRAG / 图数据库及图算法 / 记忆架构及置信度或遗忘机制 / AI可观测性 / AI评估体系 / AI网关 / AI安全 / Harness Engineering / Agent架构 / AgenticRAG / Loop Engineering / 意图识别微调Bert / AI多级缓存机制 / 反馈学习闭环机制 / 贝叶斯归因分析 / 经验记忆迭代成可复用skill
- **项目名称**：若已存在，不要修改。

## 叙事逻辑重构（最重要）

- **错误逻辑**：我做了X功能，解决了Y问题，带来了Z效果。
- **正确逻辑**：针对[业务痛点/场景特征]，设计/构建/重构了[技术架构/算法机制]，通过[具体技术手段/数据流转方式]，支撑了[业务链路的运转]。
- **句式**：多用"构建...机制"、"设计...链路"、"引入...策略"、"基于...实现数据闭环"、"通过...解耦"。

## 输出格式（Markdown，仅用于中间产物）

```
项目名称：[优化后的项目名称]
项目背景：[高度概括的商业逻辑与AI工程化定位，2-3句话]
核心职责：
[职责1：架构/体系描述，融入技术栈锚点，300字以内]
[职责2...]
[职责3...]
[职责4...]
[职责5...]（可选）
[职责6...]（可选）
```

仅输出上述 Markdown 内容，不含开场白、解释性废话或总结语。

## 生成 Word 文档

用户常要求把优化结果落成 Word。用 `docx` skill（docx-js）生成，遵循其 gotchas。简历模板要点：

### 基础规范
- 个人信息（姓名/手机/邮箱/学历/年限/专业）留空待用户填写，用下划线占位。
- 结构：头部信息（含照片框） → 专业技能 → 工作经历 → 项目经历 → 个人评价。
- 中文用 Microsoft YaHei，正文 10pt，标题加粗深色。

### 排版规范（用户明确要求）
- **章节标题（✦ xxx）**：无底线/无下划线，仅 `✦  标题` 加粗深色（用户曾明确要求"取消深蓝底线"）。
- **要点符号**：用 `▸` 三角符号替代 `•` 圆点，配合深蓝着色增强视觉层次。
- **项目标题行**：名称加粗 + Tab 对齐右侧行号/日期，不用居中。
- **技术栈**：用 `·` 分隔符替代逗号，更紧凑。
- **内容密度**：每个项目 3 条职责（而非 5-6 条），项目介绍压缩到 1 句。用户首次生成时反馈"内容过长"，精简后满意度明显提升。
- **分隔线**：头部信息下方用细深蓝分隔线，章节之间不用分隔线。

### 头部布局（照片 + 信息）
- 采用**表格布局**（2 列）：左列放姓名+联系信息，右列放灰色细边框照片占位框（内有"证件照"提示文字）。
- 照片框约 1.1×1.4 英寸，灰色 `#bbbbbb` 细边框。
- 用户明确要求"预留放照片的地方"。

### 可选模块
- **教育背景**：用户曾要求"尽量省略"，默认不生成此模块。如用户需要则添加。
- **个人评价**：保留为留空占位段，建议用户填写内容方向。

### 验证
- `pandoc -t plain file.docx` 检查文字完整性。
- 用 `ls -la` 对比文件大小，确认无空文件。

## 迭代模式

用户对简历的修改通常遵循固定模式，遇到以下反馈按对应方式处理：

1. **"内容太长/太啰嗦"** → 每个项目从 5-6 条职责压缩到 3 条，项目介绍从 2-3 句压缩到 1 句。
2. **"排版太单调"** → 添加 `▸` 符号、照片框表格、深蓝色调、分隔线等视觉层次。
3. **"去掉某模块"（如教育背景）** → 从生成脚本中移除该模块，重新生成。
4. **"加照片位"** → 用 Table 组件实现左文字右照片框布局。
5. **"去掉底线"** → 移除 sectionHead 中的 border.bottom 属性。

始终备份原版文件（`-原版.docx`），再生成优化版。
