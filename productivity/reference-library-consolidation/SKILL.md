# 参考库瘦身（手册库 / 规则库 / 提示词库）

处理一类库：**参考手册越写越多、彼此重叠、日常加载成本失控**——玩法手册、规范库、提示词库、项目文档套件、知识库 references。
用户的典型抱怨是「设定太多太杂」「怎么这么多本」「真正要用的内容反而看不到」。

本 skill 负责：**先量化取证 → 三档处置 → 索引化 → 三重验收**，并且坚持「不删在用的内容、数字要诚实」。

## When to Use

- 参考库文件数/字数明显膨胀（例如单目录 >20 本手册、>100k 字），或某个子目录占比 >25%
- 用户抱怨「设定太杂 / 找不到重点 / 内容冗余」
- 同一玩法/概念在多本手册里各写一遍（同组相似度高）
- 想把一个巨型 SKILL.md 里的索引表改成「索引卡 + 手册分册」
- 需要把 0 使用的冷门章节冷藏、把原件归档到 `_legacy/`

**不适用**：只有几份文档的小库；只要审计不要改动（只跑 `scripts/library_audit.py` 出报告即可）。

## 核心原则（四条，先背下来）

1. **合并 ≠ 瘦身**。拼接 + 去重只降「目录/查找成本」，字数可能反而上升（实测 +5.4%）。报告时**文件数、字数、索引成本分开写**。
2. **在用的内容只搬不删**。要减字只能靠「冷藏 0 使用章节」或「精简到摘要级」，且必须留原件。
3. **精简前先存档**：任何被改写的文件，都必须先存在 `_legacy/<原相对路径>` 的一份原件，否则不可回滚。
4. **索引卡是收益最高的一档**：一张 60 字的卡替代一次 5–10k 字的手册加载。

## 阶段 0：体检（先取证，别凭感觉）

```bash
python scripts/library_audit.py "<库根目录>"
```

产出 4 个指标，缺一不可：

| 指标 | 用途 | 判据 |
|------|------|------|
| 目录字数占比 | 找结构倒挂 | 某子目录 >25% 且不是核心内容 → 有问题 |
| 单文件字数 / 小节数 | 找膨胀点 | >9k 字或 >30 个 `##` 的单文件要解释理由 |
| 同组两两相似度（2-gram Jaccard） | 找可合并项 | ≥15% 视为高度重叠，可合并 |
| 使用频次（在日志/成品里 grep 名字） | 找可冷藏项 | **0 次且字数不小 → 冷藏候选** |

> 相似度、使用频次都要给具体数字。「感觉重复」不算证据。

## 阶段 1：三档处置（按收益排序）

| 档 | 动作 | 收益 | 代价 |
|----|------|------|------|
| **C 索引化（必做）** | 主 SKILL.md 只保留「索引卡」 | 最高：日常只读卡，按需开分册 | 要维护卡↔文件一一对应 |
| **A 合并同类项** | 同组手册合成一册：共用总则 + 分册（h2） | 文件数大幅下降（实测 19→8，-55%） | 字数基本不变 |
| **B 冷藏 / 精简** | 0 使用手册移入 `_frozen/` 或压到摘要级 | 真减字（实测 -24%～-31%） | 内容变薄，须保留 `_legacy` |

### 索引卡格式（照抄）

```markdown
## 🎴 索引卡

| 触发词 | 一句话机制 | 手册 |
|--------|-----------|------|
| 冻结／寸止 | 封住到达上限的权限，解除瞬间一次爆发 | `references/控制系/control-core.md` §冻结 |
```

- 路径**必须带库根前缀**（如 `references/`），否则「索引完整性」检查视为未登记
- 配套纪律写进正文：**「一次只开一张卡；卡不存在 = 不做」**

## 阶段 2：合并执行顺序（缺一步就出事）

1. **整目录备份**：`cp -r <refs> <backups>/<task>-<ts>`
   ⚠️ `cp -r src dest` 后 **dest 里直接是 src 的内容**，没有 `src/` 这一层——恢复前先 `ls` 确认。
2. 合并件结构：`# 《总纲》` → `## 共用总则`（**一张表讲清几个子项到底差在哪**）→ `## 分册：<原名>（原文全文见 <legacy 路径>）` → 原文标题整体降一级。
3. **逐行去重**：完全相同的行只留第一次出现。
4. 全局路径重写：旧路径 → 新合并件。
   ⚠️ **跳过含 `_legacy` / `分册：` / `来源` 的指针行**，否则 provenance 会自指。
5. `mv` 原件进 `_legacy/<原相对路径>`（保留目录结构，便于回滚和「见原文」指路）。
6. 校验器打补丁：**索引完整性检查必须排除 `_legacy/`、`_frozen/`、`archive/`**。
7. 三重验收：`verify`（PASS）+ `sync`（DRIFT 0）+ 断链扫描（0）。

## 阶段 3：精简（只在冷藏档做）

```bash
# 默认拒跑：必须先确认每个待改文件都有原件
python scripts/slim_markdown.py <文件> --i-have-archive <legacy 路径>
```

机械精简的边界：
- **只用于 0 使用的冷藏手册**；高使用率内容「只搬不删」
- bullet 密度高或嵌套列表的文件，`max_list` 会一口气吃掉整节（实测 4,101 字 → 245 字），跑完必须**人工看一遍字数落点**
- 精简后保留 `> 📦 本节为精简版；完整原文见 _legacy/…` 的回滚指路

## 阶段 4：报告（数字要诚实）

固定四栏，缺一不可：

1. **文件数变化**（例：手册 19 本 → 9 本）
2. **字数变化**（**可以是正数**；例：99,938 → 105,340 = +5.4%，并解释为什么）
3. **索引卡数量 / 日常加载量下降**（例：20 张 1,261 字 取代 10 万字手册）
4. **校验结果**（verify PASS / sync DRIFT 0 / 断链 0 / 备份路径）

外加一栏「**没动的部分与原因**」——避免用户以为你偷懒。

## 已踩坑清单

| # | 现象 | 根因 | 修法 |
|---|------|------|------|
| K1 | 合并完字数 **+5.4%**，被当成失败 | 拼接+去重只去掉模板行，还加了总则 | 报告里区分「体积」与「查找成本」；想真减字只能冷藏 |
| K2 | `slim()` 把 4,101 字一节压成 245 字 | 100+ 条短 bullet，`max_list` 一命中就吃光 | 机械精简只用于冷藏手册；跑完核对字数落点；在用的节还原 |
| K3 | 精简后发现**源文件没进 `_legacy`**，无法回滚 | 只归档了「被合并的那些」，独立保留的那本忘了 | 精简前断言「每个待改文件都有 `_legacy` 副本」；出事从最近一次 sync 备份恢复 |
| K4 | 合并件顶部「来源：…」四行全变成同一个路径 | 全局路径重写改到了 provenance 行 | 重写时跳过含 `_legacy`/`分册：`/`来源` 的行，改完再扫残留 |
| K5 | `verify` 永 FAIL：「N 个文件未登记」 | 索引完整性检查把归档目录也当现行 | 加 `not path.startswith('<refs>/_legacy/')` |
| K6 | 「同一字段有 4 处重复值」的假警报 | 旧单文件结构遗留：**别人的状态块嵌在自己文件里**，口径早已冲突 | 整块**迁 archive 不删**（保 baseline 与溯源），原文件留一行指针 |
| K7 | 迁移后空目录残留、外链断 | `mv` 只搬文件 | 清空目录 + 全库扫断链（占位符 `<名字>.md` 白名单） |
| K8 | 索引卡里的路径校验不到 | 卡片写的是相对路径（`控制系/x.md`），检查器认 `references/…` | 卡片一律写库根前缀全路径 |
