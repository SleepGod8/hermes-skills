## 1. LLM 批量生成，Schema 过了但语义矛盾（技能要求 vs 岗位职责），怎么自动化验证"软质量"？

**口述版**：
> Schema 只能保证格式对，语义自洽我分两层补。一层是确定性规则，判据不用关键词而是结构关系：职责里出现的技能必须落在 `hard_requirements.skills` 里、技能得跟岗位能力模型 skill_tree 有交集、level 和年限不能矛盾（senior 配 1 年直接拦）。写成断言，零成本可回归。规则抓不住隐含矛盾，就上一个独立的评审 Agent，不跟生成共用同一次调用，按 Rubric 输出矛盾对、严重度和修改建议，走同一个 Schema 校验加有限重试。两层取并集，任一层命中就报，跟合规扫描一个思路。

**边界**：一期实际只有人工抽样（10 份 / 5 人 / ≥4/5），上面是演进方案，阈值要拿真实 JD 集标定。

**追问要点**：
- 不纯用 LLM：成本、非确定性、不可回归、同模型自我确认偏差
- 防误报：技能实体用 skill_tree 做闭集映射（同义词表 + embedding 最近邻 + 阈值），映射不上只告警不拦截
- 回炉：带矛盾清单定向 revision 最多 2 轮，不过就 blocked 转人工

## 2. 多次采样的"中位/极差"阈值怎么定？极差超多少触发人工？

**先纠前提**（这题的钩子就在这）：
> 极差只对档位打分有意义，面试评分是 1-5 档才谈极差 ≤1.0。JD 矛盾是二值输出——命中/不命中，所以我看的不是极差而是 5 次采样里的命中票数：≥3 票判矛盾，2 票进人工，≤1 票放行。

**阈值怎么定**：
> 不是拍的，是拿标注集扫出来的。固定一批 JD（正常 + 人工注入矛盾），跑 5 次采样，统计不同票数门槛下的漏检率和人工接管率，取拐点。初值沿用初面评分那套口径，真实数据跑过再调。

**边界**：文档里没有实测数字，属待标定参数。

## 3. Redis Pub/Sub 消息丢了，画像和 DB 不同步，怎么不重跑流程定位是发布端没发、Redis 丢了、还是消费端失败？

**口述版**：
> 我会按 trace_id 查三处：发布端、订阅端、事实表。先看 Redis 的 `PUBSUB NUMSUB`，返回 0 就说明消息发出去了没人接——Pub/Sub 里等于直接丢了。再看日志有没有"降级到内存"的警告，那说明 Redis 当时不可用，跨节点收不到。还有监听线程有没有退出，我们那个 listener 退出只 warn 不重连，退出之后事件全丢。这几处都正常但画像还是旧的，那就不是消息问题，是读到脏缓存，查事实表最新值跟前端对一下。
> 修的时候不重跑整个流程，那样会产生新副作用：只把这一条事件按 trace_id 拿出来单条重放，消费端按 event_id 幂等去重，或者直接从事实表反向回填。
> 其实这套排查难是因为现在 `emit` 把 publish 的返回值扔了、成功也返回 False，消费端也不落处理记录，只能靠日志猜。要根治得先给事件落库做 outbox、加消费位点表。

**边界**：事件总线是架构组维护的共享骨架，他是风控/操作线联调时踩的坑。

**追问要点**：
- 日志确切格式见 `projects-fact-boundary.md` 第 3 节
- 1TB 日志 5 秒捞出：光 grep 不可能（磁盘读一遍半小时）。靠按天分区缩范围 + `rg -F -j 16 "listener 退出" 目标日目录`；真要稳定 5 秒得日志进 Loki/ES 按字段查，或在写日志时顺带打告警记录
- 该条 warning 的 trace_id 是它自己生成的，跟丢消息那次请求对不上，只能按时间窗对齐

## 4. 自动化测试发现某接口响应时间方差极大，指向哪些底层瓶颈？怎么设计压测复现？

**口述版**：
> 结合我们这个项目，抖动通常来自这几处：一是 LLM 上游——主力模型慢了就降级 DeepSeek，还有重试和退避，延迟直接翻倍；二是连接池，SQLAlchemy 和 Redis 的池子被占住，请求排队，尖峰是随机出现的；三是最容易忽略的，同步调用混进 async 里，比如 pdf 解析、SDK 同步 call 直接在事件循环里跑，一个请求就把整个循环堵住，所有接口一起抖；四是每个 LangGraph 节点都往 Redis 写 checkpoint，Redis 一慢整条链都抖；五是我们用 Redis 令牌桶限流，并发到阈值开始 429 + Retry-After，延迟呈阶梯。
> 压测我会先把 LLM 整个 mock 掉，只压自己的链路，确认是不是我这边的问题；然后固定数据集回放、跳过预热，逐级爬坡到 p99 起飞找拐点。采样每秒打点，看 p50/p95/p99 加变异系数，均值会把尖峰完全遮住；同时把连接池占用、事件循环延迟、GC、Redis RT、上游 RT 一起按时间轴对齐，一眼看出抖动来自哪层。长连接要单独测，SSE/WS 挂几百条不掉，这块最容易漏。

**边界**：性能基线文档里是 P1 验收目标，不是已跑出的压测数字。判稳定性他看 p99/p50 比值和拐点，不看方差绝对值。

**追问要点**：
- 周期性尖峰 → 先查 GC 和连接池；随机尖峰 → 资源争抢或上游
- 缓存击穿、慢查询、锁竞争是补充项，别当主线讲
