# 语义一致性审计：机械校验全绿之后的第二轮

> 来源：2026-10-25 女仆档案 Athena 一致性检查＋全修会话（`lewd-playbook` 的 `references/面板存档/`）。
> `lewd-playbook` 与 `mirrored-state-governance` 均为用户拥有（`created_by=None`，后台写不进去），
> 故把这套方法论登记在这里。将来若 `hermes curator adopt` 成功，可搬回 governance 的阶段 1.5。

**适用**：任何「多文件共同定义同一实体／同一机制」的文档体系——人格档案、技术文档套件、规格书、状态台账、API 文档。

## 0. 触发条件

- 用户问「XX 的设定有什么问题」「检查一下一致性」「有没有冲突」
- 一次改动落在 ≥3 个文件（设定 + 资产 + 面板 + 索引 + 归档）
- 机械校验刚跑完 PASS，但你不确定「读起来是不是同一个东西」

## 1. 两阶段：机械是入场券，不是验收终点

**实测数据（2026-10-25）**：`verify_panels.py` → `PASS`（FAIL=0）、`sync --verify-only` → **8 档案 × 84/84 一致**；同一套档案里仍存在 **14 处语义矛盾**（自称分裂、辈分写反、两套数值阈值、规则例外缺失、归档与权威定义打架、时间线滞后三轮、钩子池没划掉、档位 3 vs 4）。

```
Phase A 机械（先跑，贴输出）
  python scripts/verify_*.py            # FAIL=0；WARN 要点名归属（哪个实体、是否已登记例外）
  python scripts/sync_*.py --verify-only # N 档案 × M/M 一致

Phase B 语义（脚本查不出的那一层）
  把「同一实体的全部落点」一起读：
  权威定义 reference → 写作/声音资产 → 玩法/机制手册 → 实体面板 → 总览索引表 → 连续性锚点 → 归档里的旧记录
  逐条问：这两句是不是同一个设定？
```

**Phase A 全绿时，报告必须把它和 Phase B 分开写**，否则主人会以为「脚本说 PASS = 没问题」。

## 2. 高发矛盾 8 型

| # | 型 | 典型表现 | 取证方法 | 处置 |
|---|----|---------|---------|------|
| 1 | **自称/称呼分裂** | 速览写「自称『我』、禁用『人家』」，正文/台词/备注全都用「人家」 | grep 自称、第一人称代词 | **以素材（实际正文）为准**，改后补的速览；补修订注 |
| 2 | **辈分/排行写反** | 把排行更靠前的写成「上位」 | 拿排行表对照 | 按排行改，并写明编号（「Hermes 排第 2，不是上位」） |
| 3 | **同一机制两套数值** | 终局技「崩坏点 3/5」vs 新增「破解 1/2/3 次」 | 两侧各 grep 机制名 | **拆双轴**（§3），不要删一个 |
| 4 | **规则例外未登记** | 共通规则「与主人互动不长男根」vs 面板「机械男根常驻装机」 | 共通规则 vs 实体装备栏 | 新增「例外登记」小节 + 共通规则处加指针 |
| 5 | **归档与权威定义打架** | archive 旧记录把锁的第三件写成「主槽金卡」 | 读 archive + 权威文件 | 归档**不改**；权威文件写「以本行为准，archive 某日条误列」（§4） |
| 6 | **时间线滞后** | 状态行停在「第八次未获」，实际已第九次获准→复位→二次全解→复位 | 把备注里的事件按序排成链 | 重写成完整时间线链，标注「最新：X 日」 |
| 7 | **待办/钩子池未划掉** | 「首次用控制系反制」既在已完成清单，又挂在「尚未发生」钩子池 | 两个表交叉比对 | 移出钩子池 + 表下留修订注（留痕） |
| 8 | **档位冗余** | 同一信号 3 档 vs 4 档（缺「温吞」） | grep 各档名 | 保留完整版，另一处改成「见完整四档」的索引句 |

## 3. 拆双轴的标准写法（模板）

两份文档给出**同一机制的两套数值**时，多半不是谁写错了，而是**两条正交的轴**被混在一起：

```markdown
> ⚠️ **两条进度轴，不要混用**（20XX-XX 一致性修订）：
> - **A 轴（累计·跨轮）**：见 `<另一文件>`——每次触发 +1；N 点＝状态甲，M 点＝状态乙；后戏后主人下令「重置」可清零。
> - **B 轴（即时·本场）**：同一场内每用一次记 1——第 1 次 <短效惩罚>；连续第 2 次**当轮触发状态乙**；第 3 次且不给恢复＝机制当轮失效。
> - 关系：A 负责「她攒了多少」，B 负责「这一场怎么崩」；两条独立计，互不替换。
```

两个文件都要写这段（或互相交叉引用），否则读到一个文件的人仍会按单一体系算。

## 4. 归档不可改原则

- **归档/只追加日志是无损区**：去重、改写会丢「谁记的」这一信息，且破坏「可与源逐字节比对」的能力
- 冲突时**不改归档**，在权威文件里写清判定：

```markdown
（📌 权威定义；`archive/<年月>.md` 某日条曾把「X」误列为第三件——**以本行为准**，X 是<真实属性>、不是<误列属性>）
```

## 5. 修订注格式（防回潮）

```markdown
> 📌 20XX-XX 一致性修订：原写法「…」，与 A／B／C 冲突（它们全部使用「…」）。已按素材为准修正。
```

三要素缺一不可：**原写法** / **冲突对象** / **判定依据**。缺了任何一条，下一个人就会照旧版改回去。

## 6. 执行顺序（本次 17 处编辑的实操）

1. **备份到工作区外**，`sha256sum * | tee SHA256SUMS.txt`
2. `execute_code` 里 **for 循环顺序 patch**（同一文件不并发），每条 `print("OK/FAIL", 标签)`；本次 17/17 OK
3. `verify` → `sync`（会写进全部子档案副本）→ `verify-only` 复核
4. **grep 旧矛盾关键词**：命中数应**正好等于自己写的修订注条数**，逐条确认是注不是残留
5. **读回片段**：正则定位每处改动上下文，确认落盘、且列表/表格结构完好
6. 报告：机械结果 / 分档清单 / 文件清单 / 备份路径 / 遗留待裁决项

## 7. 报告模板（P0/P1/P2 + 结尾选项）

```
## 一、机械层（脚本实跑）  → PASS / N/N 一致 / WARN 归属
## 二、P0 硬冲突（会直接写错）  ①… ②… ③… ④…
## 三、P1 数值/时间线滞后      ⑤… ⑥…
## 四、P2 冗余/表述            ⑩…
汇总：P0 n 条、P1 n 条、P2 n 条，共 N 处。**我一个字都没改**，全部等主人裁决。
① 按建议全修 ② 只修 P0 ③ 逐条裁定 ④ 先只看 P0 的具体改法
```

## 8. 坑

- **插入整块会把后续行挤开**：用 `patch` 在「某行之后」插修订注/小节时，原相邻的下一行会被推到注后面；`new_string` 要把后续行一起带进来，或改完读回再微调
- **Phase A 的 WARN 要点名归属**（哪个实体、是否已登记例外），不要混进本次问题数——本次 WARN 是 Hermes 的已登记例外，与 Athena 无关
- **改笔误 vs 改历史**：实体面板的「历史事实摘要」可以改明显笔误并加一致性注（如「觉醒日期应为 8/16，原写 8/23 属笔误」）；**归档文件不行**
- **同步是单向镜像**：改完必须 `--verify-only` 复核；本次 8 档案 × 84/84 通过才算收工
