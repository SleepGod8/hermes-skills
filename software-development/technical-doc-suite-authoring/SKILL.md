# 技术文档套件编写（多文档项目开工准备）

为项目生成**一套互相引用、契约一致**的技术文档，供多 agent 开发、答辩/面试展示、团队交接使用。核心价值不是单篇文档，而是**跨文档契约一致性**——用户（主人）会做交叉分析，发现硬伤会直接打回。

## 触发条件

- 用户要求"生成项目技术文档/开发相关技术文档/文档套件"
- 为多 agent 项目准备开工文档（需求→架构→任务书链路）
- 答辩/面试项目需要完整文档体系
- 用户给需求文档/选题，要求"生成相应文档"

## 文档套件清单（7+1 件）

| 文档 | 定位 | 关键内容 |
|---|---|---|
| REQUIREMENTS.md | 最高需求权威源 | 功能点 FR 编号化（FR-x.y）、验收指标（可执行）、分期计划 |
| 01-architecture.md | 技术架构 | 分层架构、组件拓扑、核心业务流程、Agent 工作流拓扑、安全/性能/部署 |
| 02-api-design.md | API 契约（冻结） | 全局规范、统一响应/错误码、RBAC、逐模块接口 + 请求/响应 JSON 示例、契约冻结规则 |
| 03-test-cases.md | 测试用例 | 单元/接口/AI质量/E2E/安全/性能分层、用例编号 TC-模块-分类-序号、答辩证据目录 |
| 04-overview-design.md | 概要设计 | 模块划分与依赖、目录分层、ADR 清单、状态机、事件类型全集 |
| 05-database-design.md | 数据库 | MySQL 表完整 DDL、向量集合、Redis key、PII 加密、变更规则 |
| 06-detail-design.md | 详细设计 | 冻结 Schema（Pydantic）、核心算法、LangGraph 图定义、异常处理 |
| DEVELOPMENT_GUIDE.md | 多agent协作（可另出） | 固定编制分工、模型分层、门禁节奏、红线、里程碑 |

## 生成顺序与依赖

1. **REQUIREMENTS 先行**：FR 编号是全文粘合键，所有下游文档引用它
2. 架构 ← 需求；API/数据库 ← 需求+架构；测试 ← 需求验收指标 + API 契约
3. 概要/详细设计 ← 以上全部，最后写（要引用已冻结契约）
4. 每篇文档头部写"前置文档"引用链，维护者署名（按多agent固定编制）

## 跨文档契约一致性检查清单（核心价值，交付前必查）

用户交叉分析最常抓的硬伤（按严重度，均为真实踩坑）：

1. **枚举/状态值必须单一权威源**：结局标签、事件类型、状态机值在需求/设计/数据库三处必须一致。定义在 REQUIREMENTS，下游全部同步；修改要三处同改（案例：outcome_label 需求 4 种 vs 设计 3 种，漏 churned）。
2. **有表必须有 API**：数据库里每张业务表都要有对应接口驱动；没有 API 的表 = 缺口（案例：offer_orders 表设计好了但无 offer 接口，结局标签状态机无驱动入口）。
3. **身份/权限流程必须闭环**：涉及"某人如何登录/访问"必须有完整契约（注册？token？scope？过期？）；缺失会卡演示流程（案例：候选人答题 token 无发放/校验方案）。
4. **前端/界面范围必须决策**：不能"待定"或"二期再说"，E2E 演示需要浏览器界面；纯 API 演示答辩效果差。决策要写进里程碑和 DRI。
5. **概念不得混用**：事件类型 ≠ 结局标签 ≠ 状态字段（案例：outcome_label 示例值写成 offer_sent）；示例值必须符合枚举。
6. **章节编号连续性**：生成后 grep 检查编号跳号（案例：模块 4 写成 4.4.x 应为 3.4.x）。
7. **技术栈口径统一**："强制技术栈"与"实现兜底方案"要一致口径（案例：强制 Dify vs ADR 直连兜底 → 统一为"一期直连、二期接 Dify、接口预留"），答辩追问不穿帮。
8. **隐藏工作量显式排期**：评测集/合成数据/标注集的构建要进里程碑（案例：100 简历/50 匹配标注/50 问答集没排期，MS1.5 补齐）。

## 验收指标必须可执行

- 禁止"准确率≥99%"这类无测试集口径的指标——会被交叉分析打回
- 每个量化指标配：测试集规模 + 统计口径 + 评测脚本（案例：解析 F1≥0.85/100 份样本、评分一致性方差≤1.0/5次采样）
- 答辩项目强制要求：自建评测集 + 对比实验（规则 vs 向量 vs 融合）作为含金量证据

## 用户偏好（主人约定）

- **不要以"初学者"角度砍需求**：主人明确要求保留全部需求时，按专业工程视角评估可行性/分期/排期，不拿"对初学者太难"当砍需求的理由。
- **答辩/面试项目含金量公式**：含金量 = 难点 × 攻克深度 × 可验证证据（量化指标、对比实验、真实踩坑），不是功能数量。
- 讲法主线：一条端到端业务故事 + 2 个深点（如匹配可解释性、评分一致性校准）。
- 文档生成后主动做一致性验证（用 search_files grep 枚举/编号/示例值），不要等用户交叉分析打回。

## 验证步骤

1. `search_files` 检查：枚举值在全部文档出现次数与值一致、无跳号编号、无错误示例值
2. 检查每张表有对应 API、每个状态机有驱动接口
3. 检查量化指标有测试集口径
4. 汇报时列"修复了什么、验证结果"，引用具体文件路径
