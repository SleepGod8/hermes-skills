# 项目技术文档套件生成与一致性审查

## 触发条件

- 用户要求生成"全套技术文档"（需求/架构/API/测试/概要/数据库/详细设计等 5+ 份）
- 用户要求为多 agent 开发准备文档体系（立项前）
- 用户要求"交叉审查 / 排查文档一致性问题 / 还有没有残留"
- 用户要做 ToB/面试/答辩项目，需要"有含金量且契约自洽"的文档

## 文档套件清单与权威顺序

| 文档 | 性质 | 说明 |
|---|---|---|
| REQUIREMENTS（需求） | **最高权威源** | FR 编号化 + 验收指标可执行化（测试集+口径，不写"准确率≥99%"这类不可验收话术） |
| 01-architecture（技术架构） | 冻结契约 | 六层/拓扑/流程/选型理由（答辩要点）/风险对策 |
| 02-api-design（API 设计） | 冻结契约 | 统一响应/错误码/RBAC/每模块接口+JSON 示例/页面↔接口映射 |
| 04-overview（概要设计） | 设计 | 模块划分/依赖/ADR 表/状态机/事件全集 |
| 05-database（数据库设计） | 冻结契约 | DDL 级表结构/向量集合/Redis key/安全设计 |
| 06-detail-design（详细设计） | 设计 | Schema 契约/核心算法/图定义/异常降级 |
| 03-test-cases（测试用例） | 验收 | 用例编号映射 FR/证据目录/验收流程 |
| DEVELOPMENT_GUIDE（开发指南） | 协作层 | 项目全貌/固定编制 DRI/里程碑/红线/门禁 |

顺序：需求 → 架构/API/数据库（冻结）→ 概要/详细设计 → 测试 → 开发指南。需求权威源最高；冲突以下游对齐上游，修订必须回流。

## 跨文档契约一致性铁律（实战验证）

1. **需求权威源唯一**：下游文档必须与 REQUIREMENTS 同步；改需求必须回流下游，改下游不得静默偏离需求。
2. **编号可解析**：FR-x.y / TC-x-x-x / 章节号 的交叉引用必须真实存在，禁止悬空引用（例：API 引用 FR-3.9 但需求只有 FR-3.1~3.8）。
3. **枚举全局唯一**：状态机、结局标签、事件类型、角色名——所有文档同一套值，禁止一处 3 种一处 4 种（例：churned 只在一个文档里）。
4. **四类缺口模式**（交叉审查重点）：
   - **有表无 API**：表设计好了但没有接口驱动（例：offer_orders 表无 offer 接口，结局标签无入口）
   - **有事件无驱动入口**：只说"事件驱动"但没定义谁/何时/哪个接口写（例：churned 要专口 + 时机校验）
   - **有角色无账号体系**：业务要求某人登录但没账号/令牌契约（例：候选人答题无账号创建、令牌发放、scope）
   - **有里程碑无 DRI**：排了期但没人认领（例：前端页面集要显式兜底链 Aphrodite→Eos→Athena）
5. **里程碑覆盖所有工作流**：后端/前端页面集/评测集构建/文档/答辩材料都要显式排期，禁止隐藏工作量（例：100 简历评测集构建要排 MS1.5）。
6. **测试证据目录跟上测试用例**：新增 P0 用例必须补对应 evidence 文件，否则答辩证据链断。
7. **技术栈分期口径统一**：架构要求 vs 落地节奏一致（例：Dify 一期直连适配层跑通、二期正式接入），答辩被追问不穿帮。
8. **前端/技术选型只定一次**：ADR 定案后全文档同步，不留"Vue3/React"双写残留。

## 交叉审查清单（每轮逐项过）

- [ ] 全局搜索旧表述残留（旧编号 / 旧技术栈双写 / 拼写 onbaorded→onboarded）
- [ ] 所有 FR / TC / 章节引用可解析（用 search_files 验证存在）
- [ ] 状态机 / 枚举 / 结局标签全文档一致
- [ ] 表 ↔ API ↔ 事件 ↔ 驱动入口 ↔ 测试用例 五环闭环
- [ ] 里程碑 ↔ DRI ↔ 页面↔接口映射 覆盖完整
- [ ] 章节编号连续无跳号（4.4.x/5.5.x → 3.4.x/3.5.x 这类）
- [ ] 测试证据目录与 P0 用例对齐

## 工作流

1. 先建需求文档：FR 编号化、验收指标可执行化、P0/P1/P2 分级、一期/二期范围冻结。
2. 再生成架构 / API / 数据库（三者互锁：架构引用 FR，API 对应模块，DDL 对应 API 字段）。
3. 概要设计（模块 + ADR + 状态机）+ 详细设计（Schema + 算法）。
4. 测试用例：映射 FR、覆盖正常/异常/边界/AI 质量/安全、留证据目录。
5. 开发指南：项目全貌 + 固定编制 DRI + 里程碑 + 红线（PII/演示数据/禁裸 SQL）+ 待确认事项。
6. **交叉审查 ≥2 轮**：每轮修完全局 grep 验证 0 残留，再进下一轮；直到用户/审查者确认无硬伤才冻结开工。
7. 版本号升级 + 变更记录（v1.1+），OpenViking 存档核心决策（结局标签专口、API 契约、选型定案）。

## Pitfalls

- **投标书指标当验收标准**：客户文档的"准确率≥99%/2000 并发"是宣传话术，需求文档要改成"测试集 N 份 + 口径 + 达标线"，并明确无法验收的项。
- **一期二期混入**：语音面试/Vanna/PgSQL/预测归因标二期，一期不做，防范围膨胀。
- **PII 与演示数据**：候选人/简历是个人信息，演示必须合成数据 seed，禁止真实数据入库。
- **冻结契约 vs 开发自由度**：公共 Schema/接口/DDL 冻结后改动必须走 Athena 批准 + 更新契约 + 更新相关测试，禁止静默改。
