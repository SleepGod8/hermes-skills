# 技术文档包生成与契约一致性审查

## 触发条件
- 用户要求为项目生成"详细技术与功能需求 / 技术架构设计 / API接口设计 / 测试用例 / 概要设计 / 数据库设计 / 详细设计"等全套文档
- 用户提供参考文档（docx/pdf/需求文件）要求转化为可开发文档体系
- 用户要求对已有文档做交叉审查 / 一致性检查 / 找契约冲突
- 多 agent 开工前需要文档地基（REQUIREMENTS 冻结 + 下游契约对齐）

## 核心原则
1. **需求权威源唯一**：`docs/REQUIREMENTS.md` 是最高权威，FR 编号（FR-x.y）是跨文档引用契约。下游任何引用必须与需求表一致；需求改动必须回流所有引用处（API/测试/任务书/范围表）。
2. **用户需求全保留（主人铁律）**：用户明确列出的需求/功能点不因"初学者/难度"擅自裁剪。评估从**专业工程视角**进行；需裁剪/分期时显式标注并让用户拍板，绝不以"你是初学者"为理由砍需求。
3. **契约五件套互相咬合**：状态机、枚举、结局标签、角色、错误码必须在所有文档中**单一事实来源 + 全量同步**。
4. **有表必须有 API，有状态必须有驱动接口**：数据库有表但 API 无对应接口 = 缺口；状态转换表允许的转换必须有业务接口触发（或明确仅内部服务触发）。
5. **迭代审查直到 0 残留**：每轮修复后用 grep 验证旧术语 0 残留（历史方案残留是最大隐患，新旧方案并存会让开发位踩坑）。

## 工作流

### 第 1 步：读参考源，提取需求骨架
- 用户提供 docx/pdf 时先完整读取（read_file 自动提取 docx 文本），把业务需求转成 FR 编号表
- 识别"投标书/宣传文档"里的**水分指标**（准确率≥99%、杜绝幻觉、2000并发、99.9%可用率等不可验收表述），改为可执行验收口径（测试集 + 统计口径 + 双方确认）
- 保留全部业务需求点，工程化处理（分期、接口、数据模型），修订处标注"修订说明"

### 第 2 步：按固定顺序生成文档包
```
1. docs/REQUIREMENTS.md       需求权威源（FR编号 + 验收指标 + 分期计划）
2. docs/01-architecture.md    技术架构（分层/组件/核心流程/数据流/安全/部署）
3. docs/02-api-design.md      API契约（统一响应/错误码映射/RBAC/全接口请求响应示例）
4. docs/04-overview-design.md 概要设计（模块划分/DRI/ADR/状态机/时序）
5. docs/05-database-design.md 数据库设计（MySQL DDL + 向量集合 + Redis key + 安全）
6. docs/06-detail-design.md   详细设计（Schema契约/核心算法/工作流图/类结构）
7. docs/03-test-cases.md      测试用例（按FR映射 + 答辩证据目录）
8. DEVELOPMENT_GUIDE.md       多agent开发指南（编制/里程碑/门禁/红线）
```
编号习惯：01架构、02API、03测试、04概要、05数据库、06详细（REQUIREMENTS 无编号），目录排序自然。

### 第 3 步：交叉一致性审查（核心增值步骤）
生成后/每轮修复后，按 `references/doc-contract-review-checklist.md` 逐项自查。常见失败模式：
- **定义冲突**：结局标签/状态/枚举在多个文档写法不一（硬伤，优先修）
- **编号悬空**：文档引用 FR-3.9 / TC-M4-N-01 但源文档没有该编号
- **接口缺口**：有表无 API、状态转换无驱动接口、页面映射漏接口
- **残留**：旧方案术语（旧令牌名/旧状态名/旧角色/旧框架定位）在新方案改动后未清除
- **权限/安全**：请求参数信任客户端、写接口无角色约束、会话无归属校验、scope 未服务端校验

### 第 4 步：修复 + 验证闭环
- 每处修复用 patch 精确替换（先读现场再改，避免覆盖相邻标题）
- 每轮结束 grep 验证：旧术语 0 残留、新术语跨文档一致
- 审查人视角（"鲸鱼女孩"式）：从头到尾通读一遍，**只找契约冲突不找文笔**，按严重度排序输出（P0 硬伤 / P1 风险 / 毛毛刺）

## 关键技术要点（踩坑沉淀）
1. **FR 编号是契约**：需求表改一行，下游所有引用都要检查。新增功能点（如 FR-3.9）必须同步 API 引用与一期范围表。
2. **状态机要显式分支**：`draft → sent → accepted → withdrawn` 与 `sent → declined` 分开写，避免 `accepted | declined → withdrawn` 歧义。
3. **事件流三件套**：枚举（Pydantic Enum） + 状态转换表（单一权威源 core/events.py） + 事务边界（同事务 + idempotency_key + 数据库唯一索引防重）。事件、业务状态、候选人主状态必须在同一事务，任一步失败整体回滚。
4. **双码错误约定**：业务 code（42200/40000…）+ HTTP 状态映射表，前端以 code 为准，禁止裸数字无映射写法。
5. **令牌/认证方案只留一个定义**：多阶段令牌（一次性 exchange_token 兑换短期 candidate_jwt）时，旧术语（initial_token/candidate_token）必须 grep 清干净，包括测试用例和 FR 描述。
6. **权限落地三处一致**：RBAC 角色表 / 数据库 role 枚举 / permission_scope 枚举。写接口标注角色约束，scope 服务端校验不信任客户端。
7. **新接口同步五处**：API 文档 + 状态机 + 测试用例 + 前端映射表 + 数据库表注释/字段。
8. **验收指标可执行化**：'准确率≥95%' 必须配测试集与统计口径；'无人值守' 要说明人工节点如何被测试代理/固定表单代替。
9. **答辩/面试项目内建证据路径**：自建评测集 + 对比实验 + `tests/evidence/` 目录 + 演示数据 seed，量化指标是面试含金量证据（评测集构建要显式排进里程碑，别漏）。
