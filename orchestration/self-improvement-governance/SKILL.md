# 自我优化与沉淀治理流程

用于 Hermes 对自身流程、skills、提示词、配置、文档、工具用法和多档案公共能力进行系统性优化。目标不是边想边改，而是形成可审计闭环：

```text
自我检查 → 证据化问题清单 → 优化方案与优先级 → 主人审阅确认
→ 分批执行 → 每批真实验证 → 必要时修正 → 多档案安全同步
→ 独立验收 → 幂等检查 → 复盘沉淀
```

## 触发条件

用户出现下列意图时加载本 skill：

- “还有什么可优化”“自我检查一下”“复盘并改进”。
- “把刚才的方法沉淀下来”“以后都按这个流程”。
- “列清单后分批执行”“同步到所有女仆档案”。
- 更新跨项目通用 skill、protocol、runbook、模板或工作方式。
- 一个复杂任务完成后，需要把成功经验变成长期可复用能力。

不适用：

- 明确、低风险、单点修复且用户要求直接执行：直接执行并验证。
- 只要求分析、不允许修改：只完成审计和建议，不进入执行阶段。
- 项目代码开发本身：本 skill 管治理流程；具体实现仍加载项目/语言/测试 skill。

## 核心原则

1. **先查证，后建议**：必须读取真实文件、配置、skill、日志或运行结果；不得只凭印象列优化项。
2. **先列清单，后批量改**：默认在产生多项改进或涉及公共规则时，先给主人审阅清单；主人已明确要求全部按顺序执行时，可直接进入批次。
3. **批次必须可独立验收**：每批有目标、范围、风险、产物、验证命令和完成标准。
4. **修改与验收分离**：写入成功不等于完成；必须读回、静态检查或实际执行。
5. **失败是证据**：保留真实失败输出，修正根因后重跑；不得用解释代替通过。
6. **最小影响范围**：只改为目标所必需的文件，先 dry-run/diff，保留回滚点。
7. **同步不等于复制一切**：只同步明确 allowlist 的公共能力；人格、密钥、profile 私有配置默认不动。
8. **最终做幂等复核**：再次 dry-run 应无待变更；verify-only 应全部通过。
9. **选对沉淀载体**：偏好/稳定事实进 memory；可复用程序进 skill；项目约束进工程宪法；执行状态进项目控制面；不要互相混用。

## 阶段 1：自我检查与现状审计

### 1.1 确定审计范围

明确本轮检查对象：

- 一个或多个 skills。
- Hermes 配置、provider、gateway、MCP、工具调用流程。
- 项目工程规范、runbook、模板和验证脚本。
- 多 profile 之间的公共能力一致性。
- 刚完成的复杂任务中暴露的失败、重复劳动或人工步骤。

### 1.2 收集证据

至少完成与范围对应的检查：

- 读取现有 skill 主文及 linked files。
- 查找重复、冲突、过期、缺失或不可验证规则。
- 检查脚本是否有 `--help`、dry-run、错误码、备份、过滤和 verify-only。
- 检查模板是否能直接落地，是否有占位符、版本、Owner、验收证据。
- 检查多档案是否版本一致。
- 对可执行项运行静态检查或最小真实测试。

### 1.3 输出问题清单

每项使用结构：

| ID | 发现 | 证据 | 影响 | 建议 | 风险 | 优先级 |
|---|---|---|---|---|---|---|
| O-01 | `<问题>` | `<文件/命令/结果>` | `<后果>` | `<改进>` | 低/中/高 | P0/P1/P2 |

不要把“可以更好”当成问题；必须说明缺口、证据和收益。

## 阶段 2：优化清单与主人确认

把改进项按依赖和风险组织成批次：

```text
第一批：基础契约/阻断性问题
第二批：模板、脚本和自动化
第三批：文档、示例和治理
第四批：跨档案同步与最终验收
```

每批必须写明：

- 目标与非目标。
- 修改文件/skill 范围。
- 前置依赖。
- 风险与回滚方式。
- 实际验证方法。
- 是否涉及其他 profile、人格、配置或外部副作用。

### 确认规则

- 用户只问“有什么可优化”：先展示清单，等待选择/确认，不擅自写入。
- 用户说“全部执行”“按顺序进行”：视为对清单范围的执行授权，不重复询问低风险细节。
- 后续发现超出原清单的高风险修改：暂停该项并重新确认。
- 修正验证脚本、错别字或明显实现缺陷属于原批次闭环，可直接修复并重验。

## 阶段 3：分批执行

### 3.1 建立任务列表

三批及以上使用 todo，任何时刻只保留一个 `in_progress`：

```text
批次 N：修改 → 静态验证 → 真实执行 → 标记完成
```

### 3.2 每批执行协议

1. 读取当前版本和前置依赖。
2. 创建备份或确认可回滚点。
3. 做最小修改，避免顺手扩大范围。
4. 立即读回关键段落或文件。
5. 运行该批专属验证。
6. 若失败：记录输出、定位根因、修正、重跑。
7. 验收通过后才标记 completed，并进入下一批。

### 3.3 每批完成标准

- 计划内产物真实存在。
- 主文已正确索引 linked files。
- 语法/格式检查通过。
- 关键路径已实际执行；无法执行时明确阻塞与风险。
- 没有把临时文件、缓存、密钥或备份当成正式产物。

## 阶段 4：选择沉淀载体

| 内容 | 应放位置 | 不应放位置 |
|---|---|---|
| 用户长期偏好、稳定环境事实 | memory/user profile | skill 长篇流程 |
| 可重复执行的方法、命令、坑和验证 | skill | memory |
| 项目长期技术/架构约束 | PROJECT_CONSTITUTION/AGENTS | 全局 memory |
| 本轮任务、锁、验证、交接 | `.agents/` 控制面 | memory |
| 人格身份和表达方式 | SOUL.md/config system prompt | 通用开发 skill |
| 密钥值/token | 安全凭据存储/环境变量 | skill、memory、回复 |

新建 skill 前检查是否已有相近 skill；优先补强或合并，避免重复技能。复杂流程用主文 + `references/`、`templates/`、`scripts/` 分层，不把所有细节堆在 SKILL.md。

## 阶段 5：多档案同步

### 5.1 同步前

1. 明确源档案、目标档案和 allowlist。
2. 确认哪些内容是公共能力，哪些是 profile 私有内容。
3. 先运行 `--dry-run --diff`。
4. 检查差异中没有 SOUL.md、config.yaml、memories、plugins、cron、密钥和缓存。

### 5.2 正式同步

- 只同步 allowlist 中的 skill/linked files。
- 目标已存在时先备份。
- 不同步 `__pycache__`、`*.pyc`、临时文件和历史 `.bak-*`。
- 未变化项显示 `unchanged`，避免无意义覆盖和备份。

### 5.3 同步后验收

1. 对全部目标 profile 运行 `--verify-only`。
2. 验证关键文本、required files、脚本语法和模板完整性。
3. 再运行一次 `--dry-run`：应为 `would-copy=0`。
4. 检查没有缓存或私有文件污染。
5. 提醒：已打开的旧会话通常需 `/new` 才加载最新 skill。

## 阶段 6：最终报告

按以下结构汇报：

```text
结果：完成 / 部分完成 / 阻塞

1. 审计发现与批次
2. 每批实际修改
3. 新增/修改文件
4. 真实验证命令与结果
5. 多档案同步结果
6. 备份/回滚点
7. 幂等性与污染检查
8. 剩余风险和后续建议
```

禁止只说“已优化”。必须给出可核验的文件、状态和真实输出摘要。

## 失败与回退

- **写入失败**：不要宣称完成；检查路径、编码、匹配文本和工具返回值。
- **验证误报**：确认是实现问题还是 verifier 关键词过严；修正 verifier 后必须重跑完整验收。
- **同步部分失败**：停止继续扩散，保留已生成备份，修复后重新同步并全量 verify。
- **源版本本身不完整**：禁止同步；先让 source verify 通过。
- **跨档案出现定制冲突**：不要覆盖；将该 profile 排除并给主人列差异与建议。
- **memory 空间不足**：不要硬塞；压缩/替换旧条目，或把程序性知识写入 skill。
