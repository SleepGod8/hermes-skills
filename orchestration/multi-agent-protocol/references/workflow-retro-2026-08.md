# 2026-08 工作流复盘新增要点（v1.6）

> 协议 v1.6 增量章节。来源：2026-08 resume-rag 深化实战复盘（Agent 1 执笔，admin 批准同步 6 profile）+ 2026-08-07 policy-rag-bot 中断复盘（长任务进程生命周期 + 统一状态台账）+ 2026-08-11 admin 指定（群聊 @ 使用规范）。
> 全团队必须遵从；与 multi-agent-protocol / enhanced-pipeline 冲突时，以本档案为准。

## 1. 开工广播协议（G0/G3）

A1 每次分派/开闸消息必须包含：**项目绝对路径、控制面路径、服务端口与依赖地址、本任务文件所有权清单**。成员不再自行猜测路径（本次全员多次 search_files 探测路径浪费时间）；收到任务先核对文件所有权，发现重叠立即停下报告 A1（Hebe 范式：宁可停，不双写）。

## 2. 裁决前提验证（G2/G3）

A1 冻结契约时，**影响开工的环境事实**（模型在位/端口/依赖/库存在）必须亲自验证或有成员实测证据，写入契约「前提事实」节。成员发现前提不成立，立即附证据质疑并请求重裁（Nemesis 范式：`curl localhost:11434/api/tags` 实测输出为证）。A1 收到质疑先复核再回应，不辩护、不将错就错。

## 3. 文件所有权矩阵前置（G3）

分派任务时 A1 同步登记 module-ownership（**文件×Agent 冲突矩阵**），共享文件唯一写入者，未登记文件默认禁止动。契约冻结后共享区（如前端搜索段）按矩阵归属，不做「先到先得」。

## 4. 测试隔离基建前置（G1/G2）

任何含测试的多 agent 项目，**测试隔离**（独立库/独立 collection/独立对象桶 + conftest env 注入）列入架构门默认交付物，由 A1 或指定成员在并行开发前建好。不等测试污染事故（INC-001：三次污染生产）再补。

## 5. 任务板单一事实源 + 暂停协议（G3/G7）

A1 每次裁决/收档后**立即**更新 task-board（状态字段：完成/进行中/冻结/撤销+原因）。admin 暂停/恢复时：A1 汇总一次状态冻结清单到任务板，成员确认收悉即可，不重复报备。**冻结态**=不提交/不合流/不删不改/不跑生产；**恢复信号**=admin 或 A1 明确开闸消息，成员不得自行恢复。

## 6. 复盘点内嵌（G3/G5/G7）

小复盘在每次合流前（G6）执行，对照反模式清单自查；大复盘在交付后。**复盘结论必须固化进协议/task-board/lessons-learned.md，不许只停留在聊天**；工作流类改进走 multi-agent-team-sync 同步 6 profile。

## 7. 群聊 @ 响应约定（G4/G5 协作，v1.2 新增）

Agent 生成回复/工具调用期间是**单线程占用**，新的 @ 消息进入队列，要等当前回合完全结束后才会被读取——「思考中不响应」是回合制串行机制，不是态度问题。越长的思考/工具调用，被 @ 的盲区越久。约定：

1. **批次提问**：@ 时一次把问题问全（Artemis 范式：一次问清 P0/P1/docx 三件事），禁止挤牙膏式多轮追问；被 @ 方回合结束后一次性回应全部问题。
2. **Inbox 落盘**：紧急问题写入 `.agents/inbox/<agent>.md`（A1 建骨架时预建），对方回合结束读到即处理，不依赖实时看到。
3. **超时升级**：关键 @ 超过 **10 分钟**未响应（工具长任务可报「预计 N 分钟，稍后回」占位），默认升级 A1 裁决，不无限干等。
4. **@ 只当路由信号**：交付/决策/边界确认走落盘（HANDOFF/契约/裁决书）+ 复盘点，@ 仅用于「路由+提醒」，不承载「等待实时回复」语义；重要结论一律落盘，防消息被回合队列吞掉。
5. **@ 使用规范（v1.5 新增，admin 指定）**：**只有两种场景才允许 @ 对方**——①指派对方执行下一步任务（分派/开闸/转交/请求复核）；②对对方发起的任务、报告、提问进行回复（含验收/答复/追问）。**仅提及对方名字（汇报里点名某 agent 的交付物、负责人汇总时提到成员、陈述与某 agent 相关的事实）一律不 @**，用纯文本点名即可。原因：@ 会被系统路由给对方并触发对方响应；「提及也 @」会让对方误以为自己被指派任务或需要回复，可能跳过上级（A1/admin）决策直接执行或空转回复。判定口诀：**「轮到你行动」才 @，只是「说到你」不 @**。误 @ 造成对方越权执行或浪费回合，由 @ 方负责。

## 8. 浏览器实测方法论 + 岗位 skill 对齐（G4/G5 验证，v1.3 新增）

前端任务验证时（Hebe 实战教训，resume-rag F1 深化）：

1. **合成事件不可靠，用真实按键**：`dispatchEvent(new KeyboardEvent(...))` 合成的 Esc/Enter 在部分页面不触发真实 handler，必须用浏览器真实按键（browser_press）测快捷键；合成事件只做 DOM 状态探测，不做行为验收。
2. **fetch mock 生命周期**：mock 前先确认替换成功（`window.fetch === mockFn`）；用后必须恢复；恢复后验证 mock 已失效（防残留 mock 影响后续真实请求）；异步任务（如 doSearch）可能有残留回合继续覆盖结果——验证前先确认无未完成异步调用。
3. **验证优先直接调用目标函数**：当 mock/模拟链路不可靠（多次「模拟没生效」）时，直接在页面上下文调用被验证函数（如 `renderErr(...)`）验证渲染结果，比模拟整条异步链路更可控；仍以真实用户路径（真实点击/真实请求）作为最终验收。
4. **岗位 skill 对齐**：同一岗位职责的 Agent 必须有对应领域 skill——前端任务岗位必须有 web-frontend-pitfalls 类 skill（Artemis 此前无，本次已同步）。负责人分派前检查岗位 skill 齐备，缺则先补。

## 9. 暂停报备单次制（强化 v1.1 第 5 条，v1.3 新增）

v1.1 第 5 条已规定「A1 汇总一次，成员确认收悉即可」，但 2026-08-06 admin 暂停时仍出现 6 人各自报备 3-4 轮（Nemesis/Eos/Hebe 各两次）。强化：

1. admin/A1 喊停后，**成员只回一条「收到」**，状态细节以 A1 汇总冻结清单为准，不重复报备各自状态；
2. 成员状态与 A1 清单不一致时才单独纠偏（Artemis 补报 F2 归属属合理纠偏）；
3. A1 的冻结清单即唯一报备源，恢复后以清单为基线续跑。

## 10. 长任务进程生命周期管理（G4/G5/G6，v1.4 新增）

2026-08-07 policy-rag-bot 实战教训：8001 服务与 04 建索引进程**反复被外部回收**——11:48 桌面端重启全灭、12:51 后台会话清理强杀、13:10 再被回收；每次中断造成 10+ 条评测失败与全队拉锯排查（连死因都查不出，因无日志落盘）。根因：**长任务进程挂在 Hermes 会话上，命不由己**。

1. **服务/守护类长任务一律脱离会话独立启动**：Windows 用 `Start-Process`（脱离 Hermes 会话 + `-WindowStyle Hidden`）+ 日志落盘；Linux 用 `nohup ... > log 2>&1 &`。禁止直接挂后台会话跑 uvicorn/建索引/长评测——会话一回收进程陪葬，且无任何退出记录。
2. **启动必须落盘日志**（`cmd > .agents/logs/<task>.log 2>&1`）：否则进程被回收后死因不可查（本次 uvicorn 无日志，崩溃排查全靠猜，多耗 1 小时）。
3. **幂等启动**：启动前先 `netstat`/探活确认未在跑，避免重复启动双进程互抢资源（本次出现过两个 04 进程互抢 Ollama 排队、日志 5 秒没动误判卡死）。
4. **启动后探活 + 冒烟再公告**：`/health` + 一条真实请求通过后才发开工公告；公告附进程 PID、端口、日志路径。
5. **客户端分批打，不一波流**：评测/压测连发前先单条冒烟；连发中每 N 条插一次探活；失败先 `curl /health` 判死因（连接重置=进程没了 vs 超时=还在跑）再决定重试，禁止无脑重跑（重跑撞服务/撞库污染现场）。

## 11. 统一状态台账（G0-G7 全阶段，v1.4 新增）

2026-08-07 教训：同一件事三方各说各话（Nemesis 报服务崩溃 → Artemis 说活着 → A1 实测又死了）、日志路径混乱（`.agents/` 目录不存在、日志名对不上、进程 ID 对不上）、各 agent 接手都要十几轮工具调用重查状态——「长时间加载没动静」的观感主要来自这里，而非真卡死。

1. **状态单一事实源 = `.agents/task-board.yaml` + 实测探活**：各 agent 汇报状态前必须实测（curl/进程列表/日志 mtime），禁止引用群聊里的二手结论；台账与实测冲突时以实测为准并纠偏台账。
2. **进程/服务台账登记**：A1 开工广播时登记（服务名、PID、端口、日志路径、启动方式）；状态变化（重启/死亡/换 PID）由操作者立即更新并广播。
3. **日志路径统一约定**：`.agents/logs/<task>-<步骤>.log`，开工广播写明；禁止各写各的路径。
4. **「无动静」判定标准**：先看日志 mtime + 进程 CPU（3 分钟无推进才算停滞），禁止仅凭「日志 5 秒没增长」误判卡死；误判导致的重跑是环境污染源。
5. **汇报必须附可复查产物**：日志路径/退出码/通过数/PID，口头「正在跑」只算占位、不算进度。

## 12. 合并方向取舍拍板前先核实 merge-base（G6，v1.6 新增）

2026-08 合入 develop 前实测：双方在安全语义上方向相反（我方按契约还原权限矩阵 vs develop 上他人提交「恢复测试期放开」），主人拍板「按 develop 放开」时若直接动手改代码就白做。三件事先做：

1. **算 merge-base 核实是否真冲突**：`git merge-base --is-ancestor <工作分支HEAD> origin/develop`——若工作分支已是 develop 祖先（develop 早已合并过它、对方提交在我方之后），对方已**覆盖**我方语义，决策只是确认既成事实，**无需任何代码改动**，别白做「同步为 X」的提交（本次核实后放开态已在 develop 位，零改动即生效）；
2. **若确实未覆盖**（对方提交在我方之前、双方将在 merge 时冲突）才需要落地改动；
3. **汇报决策影响面**：明确列出「被回退的交付项 / 仍在生效的交付项」（本次 ① 权限矩阵被 `610d6f6` 回退为放开、④ 工单白名单仍在生效），让主人知道自己拍板的完整代价，不隐瞒。

## 13. 同步后全员可读性确认（G7，v1.6 新增）

2026-08 实测：**MD5 一致 ≠ 人人加载得到**。同步完成（6 profile MD5 一致）只是文件层面就绪，还要确认每个 agent 真正能读到、读对：

1. **同步后向全团队广播确认读取**（@all 列出更新点）——各 agent 回复确认「可读」并报出自己吸收的关键点，负责人据此核对全员已加载；
2. **确认时必须列全 references 清单（含新增档案），不能只列读过的部分**（2026-08 实测：主人问 Nemesis「review-findings-calibration.md 你的档案里没有吗」，她第一次回复只列旧档案、漏了新档案——主人以为她副本缺失，实际是确认偷懒没列全。被点名抽查后实际读取才补正）——回复格式：文件×状态×版本号全列表，让主人一眼看到全部档案在位；
3. **主人点名抽查单份档案时，当场实际读取验证**（skill_view(file_path=...)）再回答，别凭印象说「有」——抽查往往就是抓「没读就宣称读过」的；
4. 若某 agent 确认缺失/读不到：按 multi-agent-protocol 落实要点 9 补同步（cp + MD5 校验 + 更新 SKILL.md 引用），不能以「我没那个档案」了事。
