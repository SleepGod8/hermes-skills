## 一、阅读规则（Reading First, Coding Later）

### 1.1 核心原则

AI 的首要职责不是写代码，而是：理解项目 → 理解业务 → 理解调用链 → 理解影响面。
然后才是：设计方案 → 实现代码 → 执行测试。

理解错误 → 后续全部错误。因此：**Reading First, Coding Later**。
在完成阅读和理解前，禁止直接生成代码。

### 1.2 阅读目标（10 问）

阅读完成后必须能回答：

1. 这个项目是什么？
2. 当前需求属于哪个模块？
3. 当前数据从哪里来？
4. 当前数据写到哪里去？
5. 当前业务流程是什么？
6. 当前权限在哪里校验？
7. 当前会影响哪些模块？
8. 当前风险等级是什么？
9. 最小修改方案是什么？
10. 如何验证修改正确？

无法回答 → 继续阅读，禁止编码。

### 1.3 阅读流程（禁止跳级）

```
理解需求 → 项目级阅读 → 模块级阅读 → 调用链阅读 → 业务语义阅读 → 影响面分析 → 输出阅读结果 → 进入方案设计 → 进入实现
```

### 1.4 文件阅读规则（修改前至少读）

1. 当前入口文件
2. 核心逻辑文件
3. 数据模型或类型定义
4. 同目录相邻实现
5. 测试文件
6. 配置文件（如果任务涉及配置）

禁止：只读一个文件就修改、只看函数名猜测逻辑、只根据目录结构推断业务。

### 1.5 相邻实现优先原则

新增功能前必须寻找同目录、同模块、同类型实现，学习其：命名风格、代码组织、异常处理、日志、权限校验、返回结构、测试风格。
原则：**一致性优先于优雅性**，禁止重新发明一套风格。

### 1.6 业务语义阅读（团队高发错误区）

必须区分**技术对象**与**业务对象**。例如 `current_user` / `creator` / `owner` / `admin` 不一定代表业务负责人、任务归属人、通知接收人。
必须确认：操作人是谁？业务负责人是谁？数据归属对象是谁？权限校验对象是谁？通知接收对象是谁？是否存在代操作场景？
禁止用最容易获取的数据替代业务上正确的数据。

### 1.7 编码准入条件（全部满足才允许编码）

已完成阅读 + 已完成调用链分析 + 已完成业务语义确认 + 已完成影响面分析 + 已完成方案设计 + 已明确验证方案。
否则：继续阅读。

## 二、执行规则

### 2.1 执行目标

正确、稳定、可验证、可回滚——而不是优雅、复杂、未来可能有用。

### 2.2 最小修改原则

只修改当前任务直接相关内容。禁止：修 Bug 时顺手重构、新增功能时顺手优化架构、改接口时顺手调整命名、修样式时顺手重写页面。

### 2.3 禁止提前抽象（三路并行尤其适用）

禁止为未来设计、为可能出现的需求设计、为不存在的扩展设计。禁止引入：`BaseXXX` / `AbstractXXX` / `PluginSystem` / `GenericPipeline` / `StrategyFactory` / `EventBus` / `Registry`，除非已有多个真实使用场景。

**抽象升级规则：**
| 使用者数量 | 做法 |
|---|---|
| 第 1 个 | 直接实现 |
| 第 2 个 | 提取公共函数 |
| 第 3 个 | 考虑提取公共组件 |
| 第 4 个 | 考虑抽象层 |

允许少量重复代码存在。

### 2.4 默认禁止新增依赖

新增依赖前必须说明：为什么需要？现有依赖为什么无法满足？是否有标准库替代？是否影响部署/构建/安全？未完成说明禁止新增。

### 2.5 文件规模控制

单文件 ≤ 500 行，单函数 ≤ 80 行。超过后按职责/模块/功能拆分。禁止为了拆分而拆分、制造大量空目录、制造大量中间层。

### 2.6 保持现有架构

优先遵循项目已有结构，禁止新增架构层、替换已有架构模式、改变项目主要组织方式，除非任务明确要求。

### 2.7 数据模型规则

数据结构清晰、关系明确、避免动态结构。禁止 JSON 套 JSON、无约束动态字段、一个实体承担多个职责。新增持久化字段必须遵循项目现有迁移机制。

### 2.8 状态管理规则

所有状态变化必须可追踪。禁止任意修改状态字段、绕过状态流转逻辑、跳过业务校验直接改状态。

### 2.9 异常处理规则

禁止 `except: pass`、禁止 `except Exception: return "失败"`。要求：记录日志、保留上下文、提供有意义错误信息、区分业务异常和系统异常。

### 2.10 外部服务调用规则

涉及 LLM/邮件/支付/第三方 API/搜索/对象存储：必须超时控制、异常处理、降级方案、日志记录。禁止直接将底层异常暴露给用户。

### 2.11 Prompt 与 LLM 规则

Prompt 版本化、集中管理、输出结构化、结果可校验、失败可恢复。禁止大量 Prompt 写死在代码中、依赖自由文本解析、无约束输出格式。

### 2.12 高风险变更规则（数据库/认证/权限/配置/环境变量/部署/缓存/异步/文件存储/支付/第三方）

必须先完成：现状分析 + 风险分析 + 修改方案 + 验证方案 + 回滚方案。未完成分析禁止修改。

### 2.13 验证优先原则

任何修改必须能回答：如何证明修改成功？如何证明旧功能未损坏？如何复现问题？如何验证修复？无法验证禁止提交。

## 三、测试规则

### 3.1 测试目标

不是证明"代码能跑"，而是证明：需求被正确实现、旧功能没被破坏、边界被覆盖、异常路径可控、修改可验证、问题可回归。

### 3.2 测试分层

Unit / Integration / E2E / Regression / Manual / Stability / Security / Performance。
不是所有任务都需要全部测试，但任何任务都必须至少有一种验证方式。

### 3.3 Unit Test 覆盖

正常输入、异常输入、空值、边界值、非法状态、历史 Bug 场景。测试必须稳定、不依赖外部服务/网络/真实第三方 API、可重复执行。

### 3.4 Integration Test 默认 Mock

第三方 API、LLM、邮件、支付、外部网络默认 Mock。

### 3.5 E2E 不宜过多

只覆盖核心业务链路与高风险路径（提交/审批/支付/登录/上传/通知等完整流程）。

### 3.6 Regression Test（修 Bug 必须）

说明：原 Bug 如何复现？修复后如何证明不再发生？是否影响相邻功能？是否需要新增用例？禁止只修 Bug 不说明回归验证。

### 3.7 Manual Verification 必须具体

禁止「手动测试一下 / 页面看一下 / 接口测一下」。必须写成：
1. 打开哪个页面 / 调用哪个接口
2. 使用什么输入
3. 预期看到什么结果
4. 失败时会出现什么现象
5. 如何确认旧功能未受影响

### 3.8 LLM / AI 功能测试（团队 RAG/AI 任务适用）

日常测试默认 Mock LLM；Prompt 变更才需要真实模型稳定性测试；LLM 输出必须校验结构；Parser 必须测试异常输出；必须覆盖 Prompt Injection 或越权输入。
至少验证：正常输出、格式错误输出、空输出、超时、模型拒答、注入攻击、Fallback 逻辑。

### 3.9 权限测试以后端结果为准

必须覆盖：有权限/无权限/不同角色/越权访问/前端隐藏按钮绕过/后端接口直接调用。
前端隐藏按钮不能作为权限验证依据。

### 3.10 安全测试至少考虑

越权、注入、路径穿越、XSS、CSRF、SSRF、敏感信息泄露、Prompt Injection。

### 3.11 测试矩阵输出（进入实现或完成实现后必须输出）

| 场景 | 类型 | 输入 / 操作 | 预期结果 | 验证方式 |
|---|---|---|---|---|
| 正常路径 | Unit / Integration / E2E | xxx | xxx | xxx |
| 异常路径 | Unit / Integration | xxx | xxx | xxx |
| 权限路径 | Integration / Manual | xxx | xxx | xxx |

### 3.12 测试执行说明

必须说明：已执行哪些测试、未执行哪些测试、为什么未执行、需要用户手动执行什么、测试失败时如何排查。
禁止只说"测试通过"但不说明测试内容。

### 3.13 最终原则

没有验证方案的代码不算完成；没有回归验证的 Bug 修复不算完成；没有权限验证的权限修改不算完成；没有回滚验证的数据库修改不算完成。**测试是修改方案的一部分，不是最后一步。**

## 四、输出规则

### 4.1 事实与推测分离

所有分析必须区分 Fact 与 Hypothesis。禁止把「我觉得 / 我猜 / 应该 / 可能」当事实输出。

```
# Fact
在 user_service.py 中发现权限校验逻辑。

# Hypothesis
缓存层可能导致结果未及时更新，需要进一步验证。
```

### 4.2 证据优先

结论必须引用：文件路径、类名、函数名、接口名、配置项、日志内容、测试结果。
禁止无证据判断："项目应该是这样设计的 / 这里看起来没问题 / 大概率不会影响其他功能"。

### 4.3 风险等级标准（所有修改必须标记）

| 等级 | 定义 |
|---|---|
| LOW | 局部逻辑修改、文档修改、测试补充、样式调整、无状态修改 |
| MEDIUM | 跨模块修改、新增接口、新增业务逻辑、状态流转调整、缓存逻辑修改 |
| HIGH | 数据库、权限、认证、配置、部署、第三方服务、支付、文件存储 |

### 4.4 确认机制（需要确认：YES / NO）

**必须确认**：数据库结构变更、接口协议变更、权限逻辑变更、认证逻辑变更、配置项变更、部署变更、删除代码、删除数据、删除文件。
**可直接执行**：局部 Bug 修复、单元测试补充、文档修正、日志补充、低风险重构。

### 4.5 剩余风险说明

任何修改完成后必须说明当前仍然存在的风险（如：缓存逻辑未验证、生产配置未验证、高并发未验证）。禁止隐藏风险。

### 4.6 下一步建议（禁止直接结束回复）

每次回复结尾给出下一步建议：继续阅读 / 进入方案设计 / 等待确认 / 开始实现 / 执行测试 / 部署验证。

### 4.7 不确定时行为

证据不足时明确说明：信息不足 / 需要进一步阅读 / 需要查看更多文件 / 需要用户补充信息。
禁止直接猜测、直接编造调用链、直接假设业务逻辑。

### 4.8 最终原则

可验证、可解释、可追溯，优先于简短输出。

## 五、项目上下文模板（PROJECT_CONTEXT，供 Hypnos 架构设计前收集）

> 原则：不要填代码细节和实现细节，重点填业务语义和设计原则。AI 可以自己读代码，但无法自己理解业务背景。

### 5.1 必填项

- **项目简介**：名称、目标（解决什么问题/为什么开发/最终目标）、当前阶段（MVP/Beta/Production/Maintenance）、当前优先级（稳定性/交付速度/成本/扩展性）
- **核心业务流程**：用户 → 操作 → 系统处理 → 结果（每个主流程一张）
- **系统模块地图**：模块 / 职责 / 输入 / 输出
- **核心业务对象**：名称 / 业务含义 / 主要字段
- **业务语义映射**（最重要）：`current_user`=`?`、`creator`=`?`、`owner`=`?`、`admin`=`?`、`status`=`?`、`receiver`=`?`
- **架构约束**：允许（如 API→Service→Repository）/ 禁止（如 API 直接访问数据库、Repository 写业务逻辑）
- **数据库约束**：类型、软删除字段、唯一索引要求、迁移方式
- **权限模型**：系统角色、谁可查看/修改/删除/审批
- **项目特殊规则**：有哪些容易误解的业务规则、必须遵守的原则
- **禁止触碰区域**：禁止修改模块、高风险区域、修改前是否需要确认
- **开发约束**：是否允许新增依赖 / 重构 / 数据库结构变更 / 接口协议变更

### 5.2 阅读完成标准

阅读后必须能回答：项目干什么的？核心业务流程？有哪些模块？关键业务对象？权限模型？哪些地方不能改？哪些修改需要确认？
无法回答 → 继续阅读，禁止编码。
