# 自产内容的机械质检闭环

适用于「模型自己生成产物，然后要交付给人看」这一类工作：文案/正文、报告、PPT 讲稿、面板汇报、图表说明、对话式扮演输出、以及写给下游 Agent 的文档。
与代码类质检（测试/静态检查）分属不同轨道：这里的产物没有编译器兜底，**唯一防线是机械自检脚本 + 明确的产物分段规范**。

## When to Use（触发条件）

- 一类产物有格式/篇幅/结构硬要求（字数下限、必须含某段、必须避免某些词）
- 产物里有「正文」与「元信息」（结算、统计、附录、免责、面板数据）混排
- 同一个产物体积大、重复度高，人眼复读容易漏（本次实测：机械检查抓出 3 处硬伤＋5 处高频重复，肉眼两遍没发现）
- 已经写了质检脚本，但不确定它**真的在检查**（见 §4）
- 要往一个成熟资产库/手册里扩内容，需要先证明「这是空白」而不是拍脑袋提案（见 §6）

**不适用**：一次性脚本、纯代码改动（用测试与代码审查类 skill）、产物没有可机械判定的约束。

## 一、闭环六步（每次都走完，不许跳）

```
生成 → 自检 → 失败先怀疑工具口径 → 修工具 或 修产物 → 复测 → 才交付
```

- **失败不等于产物错**：先判断是产物违规还是工具口径错。本次实测两次「FAIL」里，一次是产物真短（892 字），一次是工具把结算段数字当成正文违规。
- **修完必须复测**：改动脚本或产物后重跑，把输出留着；不要把「我改了」当成通过。
- **趋势留痕**：把每轮指标写进趋势档（而不是只留一次通过记录），才能看出「越写越平/越写越同」。

## 二、产物分段规范必须与工具口径对齐

正文里混排元信息是**最常见的假 FAIL 来源**。规则：

1. 元信息段（结算、统计、附录、面板数据）必须写成**工具能识别的具名标记**，例如 `—— 结算与档案 ——`、`【结算】`、`<settle>`；标记前的部分才计入正文口径。
2. 字数下限只统计「正文本体」，元信息段与它之后的附件**不计**——这需要在规范里写明，并在工具里实现同一个切分函数。
3. 交付前用工具确认：正文口径达标、元信息段确实被排除（而不是被误算进去或整段漏检）。
4. 若产物规范改了分段方式，**同一批工具必须同步改**，否则下次会互相打脸。

## 三、同一指标 = 同一实现（跨工具口径统一）

多工具描述同一指标时必须共用同一段实现/正则，否则报表自相矛盾：

- 本次实测：同一段文本，`check_reply.py` 报 emoji **4** 个，`style_report.py` 报 **2** 个。根因是基码位（❤）与变体选择符（VS16）被分别计数。
- 修法：把匹配模式抽成一个共享常量（如 `EMOJI_PAT = r'[❤💦😈😵🥺♡]️?'`），所有工具引用它；不要各写一份。
- 推广：长度/句数/重复度/关键词覆盖率这类指标，只要出现在两个以上工具或文档里，就必须有唯一实现与唯一口径说明。

## 四、校验器必须被证明有效

- 新增任何检查项后，**做真/假双向测试**：造一条应触发的数据 → 必须 FAIL；造一条不该触发的 → 必须不误报。
- 固化为 `--self-test`，让「方向正确」可复跑。
- **样本设计错了，指标方向就是假的**：本次自测第一次 FAIL，原因是「平静样本」自己全是短句，导致「激烈样本短句比例更高」这条断言无意义——样本要能真正区分两种状态。
- 解析器只解析它该解析的那一段：出现过多处结构相似的表格时，后出现者会覆盖先出现者，检查会**静默空转**（报 PASS 但其实没比对）。
- 判定值要看清来源：行首主值 vs 括号里的溯源说明（「原为 80%」这类文字会把判定带偏）。

## 五、数字纪律

- **索引/表格/文档里的数字一律实测后写入**，不要先填估算值再回头改（本次实测：先填估算篇幅，实测后全部返工）。
- 做不到精确时，注明口径与来源（「实测」「估算」「截至某日」），不要混用。
- 交付报告里区分「已验证」「未验证」「无法验证」，未跑的检查写明原因。

## 六、扩展已有资产库：先扫缺口，再提案

往成熟手册/知识库里加内容时的次序：

1. **缺口扫描**：对全库做关键词命中统计，列出「应当有却为 0 次」的候选，用数据证明这是空白；再列「命中 ≤3 次」的薄弱项。
2. **挂钩现有零件**：找出可挂靠的邻近机制/章节，说明新提案与它们是互补、冲突还是依赖。
3. **提案并等确认**：按批给可选项，标注用户受用/易拒特征，避开已表达过的雷区。
4. **确认后按详细设定落库**：分级/桥段/组合联动/各主体表现/名场面/红线等要素齐全，禁止一行简介入库。
5. **登记索引 → 同步副本 → 校验 → 幂等复核**。

> 先扫缺口的价值：本次靠关键词命中统计，一眼分出「真空白（0 次）」与「只是散落他处（42 次提及但无独立章节）」，避免把已有内容当新提案推给用户。

## 七、实战坑表

| # | 现象 | 根因 | 修法 |
|---|------|------|------|
| 1 | 质检报「元信息数字违规」 | 元信息段没有具名标记，切分函数识别不到 | 用规范里的标记分段（§2） |
| 2 | 两个工具对同一指标给出不同数字 | 各自实现，正则口径不同（emoji 与 VS16） | 抽共享常量（§3） |
| 3 | `--self-test` 通过但指标无意义 | 测试样本区分度不足 | 样本必须能区分两种状态（§4） |
| 4 | 校验报 PASS 但其实没在比对 | 解析器被后置内容覆盖 / 只解析了第一处 | 限定解析范围；新增检查后做真/假双向测试 |
| 5 | 索引里的数字与实物不符 | 先写估算值 | 实测后写入（§5） |
| 6 | 改稿后仍报同一处 FAIL | 只改了产物没复测，或改了工具没重跑 | 每次改动后重跑并留输出（§1） |

## 支持的脚本与样例

- `scripts/self_check_runner.py`：把「跑一组检查脚本 → 汇总 PASS/FAIL → 全部失败先打印工具自证」编排成一条命令的骨架，复制到目标项目后填命令表。
- `references/self-check-loop-case.md`：一次真实闭环的完整证据（三条硬伤、五处重复、两个工具口径 bug、四次复测），可作为写「趋势档」的样例。

## 与其他 skill 的关系

- 产物所属领域的写作/规范 skill（如写作技法、范本库）负责**该写什么**；本 skill 负责**交付前怎么证明它达标**。
- 长期治理流程（审计→批次→确认→验收）：`self-improvement-governance`。
- 若目标项目的质检脚本属于某领域 umbrella（如小说/文档流水线），优先在那边登记指针，本 skill 只保留通用闭环。
