# Agent 任务书生成（vibecoding 项目开工准备）

## 触发条件
- 用户拿到项目文档/骨架，要求"整理成方便给 agent 读取执行的文档"
- 需要为某个域/模块准备开发任务书（DRI 边界、契约、验收）
- 项目开工前需要数据缺口分析或对齐提案
- 用户说"分析我负责的内容需要完成什么业务功能/业务逻辑/还有什么没考虑到"

## 工作流程

### 第 0 步：材料证据预处理（按需）

如果任务输入包含用户明确指定的图片、PDF 或扫描文档，先使用 `persona-distillation` 生成 `ocr-report-v1` 来源报告和证据分级。任务书只引用来源 ID、报告路径和已确认结论；不得把 OCR 原文、低置信度内容或敏感字段直接写成任务硬约束。冲突和待确认项必须保留在任务书的待确认/对齐提案部分，主人确认后再定稿。

### 第 1 步：侦察文档体系
先读仓库顶层（README / AGENTS.md / docs 索引），定位：
- 项目总章（AGENTS.md）→ 全局铁律、DRI 矩阵、文件所有权
- 角色文档（docs/02-roles/<域>.md）→ 该域的原子任务、写权限目录、Done 条件
- 冻结契约（docs/01-architecture/ 的 DDL/接口/事件/Tool/错误码）→ 不可改的约束
- 权威源（需求/功能设计/规则文档）→ 参数细节

### 第 2 步：提取 DRI 边界
明确：写哪些文件、只读哪些域、协作方是谁、跨域走哪些公共接口（tool/event/API）。
**注意分工可能与用户口头理解不同**——以最新文档矩阵为准，发现差异要明确告知（例：用户以为负责风控+操作，最新矩阵已把操作拆给同事）。

### 第 3 步：识别契约差异（关键增值点）
比对需求文档 vs 设计文档 vs 规则文档，找出不一致：
- 规则/接口编号（R001 vs RW-001）
- 阈值参数（7天≥10次 vs 7天≥20笔）
- 权限归属（需求没写转账权限，设计文档写了）
- 文档 vs 代码（基类命名 AgentBase vs BaseAgent；文件头维护人 vs DRI 矩阵）
每项进"待确认清单"，给**建议默认值 + 不采纳的后果**，让决策方只需说"同意/改"。

### 第 4 步：生成任务书
结构模板（用户已验证有效）：
```
# <域> · Agent 任务书（DRI: xxx）
## 0. 用途与使用方式（喂 agent 的开场指令 + 权威源优先级）
## 1. 负责内容（DRI 边界表：写/只读/协作方）
## 2. 任务需求（原子任务表 + 分级/流程铁律 + 需要实现的 API）
## 3. 所需技术栈（语言/框架/存储/关键约束）
## 4. 核心资产（规则/意图全量表：编号/参数/等级——参数必须与权威源核对）
## 5. 代码做法（文件清单与现状 + 实现要点 + 测试要求）
## 6. 接入骨架（抽象方法实现示意）
## 7. 边界（不许越界清单）
## 8. 红线（违反=返工）
## 9. 验收标准（Done 勾选清单）
## 10. 参考文档索引 + 待确认/已确认事项
```

### 第 5 步：数据缺口分析
把"功能/规则需要的数据" vs "现有表字段"逐条比对（用 `sql/create_tables.sql` 实测，别只看文档）：
- ✅ 可直接实现 / ⚠️ 部分缺口 / ❌ 严重缺口
- 缺口字段清单：字段名、服务于哪条规则、建议落点（加字段/新表/配置 mock）、优先级
- 常见缺口模式：对手方字段缺失（交易表没 counterparty）、身份字段缺失（无身份证/手机号）、名单数据缺失（制裁/PEP/黑名单）、变更历史缺失、定时调度机制未定义

### 第 6 步：对齐提案（给架构组）
- 每事项：现状 → 影响 → 建议默认 → **不采纳的后果**（"验收会挂"比"建议优化"有力）
- 一页决策汇总表 + 时间线
- 标注哪些事项阻塞开工（P0），哪些可会后确认

## 关键技巧
1. **参数必须与权威源逐条核对**：文档读取被截断时不要凭推断写参数——补读完整原文再落表。任务书参数写错 = agent 实现错规则（例：RW-012"30日≥6次"实为"申购≥3次且赎回≥3次且持有期<7天"）。
2. **用实测证据**：DDL 用 `grep -c "CREATE TABLE"` + 实际建表语句确认，别信文档摘要。
3. **给 agent 的任务书要"零歧义"**：契约编号、阈值、权限矩阵全部具体化；红线里明确"禁止 TODO/假成功、PR 级别、错误码"。
4. **生成后主动发现矛盾**：任务书里标注"待确认事项"，用户拍板后更新为"已确认结论表"（保留决策记录）。
5. **配套产物**：任务书 + 数据缺口清单 + 对齐提案，三件套放仓库根目录（RISK-*.md 命名风格），喂 agent 时指定读任务书。
6. **文档归属注意**：docs/ 通常归架构组 DRI——任务书这类个人产物放仓库根目录，不污染 docs/。
7. **配合多 agent 执行（framework-first）**：任务书定稿后别把所有实现单元一次性并行派发——先串行做共享框架（骨架类/接口签名/conftest 测试基建），**冻结接口**后再把独立单元（如每条规则、每个 handler）分给 2-3 个 delegate_task 子代理并行实现；子代理 context 给足（任务书路径 + 该单元权威参数 + 冻结接口 + 测试要求），合并后跑 pytest 验证。设计决策类工作（方案选型、PENDING 契约）单 agent 更强，别并行。
8. **任务书参数被权威源修正后要回流**：用户拍板（如"转账仅客户经理""规则 4 档为准"）后把"待确认事项"升级为"已确认结论表"；发现参数错（如 RW-010/012/015 与权威源不符，一次修 8 处）必须立即改任务书再让 agent 开工，否则 agent 按错参数实现规则必返工。
