# Agent 执行任务书编写

把项目文档（需求/功能设计/规则/契约）提炼成 AI agent 可直接读取执行的任务书。实测于金融多 Agent 项目（智能财富管家，7 人 5 天 vibecoding）。

## 触发条件

- 用户给出需求文档/规则文档/契约，要求"整理成方便给 agent 读取执行的文档"
- 用户要为某个开发域准备任务书/开发规格
- 需要分析项目文档找出数据缺口、契约冲突、待确认事项

## 任务书七要素（SKILL.md 结构）

1. **负责内容**：角色 / DRI / 写权限目录 / 只读域 / 协作方——文件级所有权（谁的文件谁写）
2. **任务需求**：原子任务表（编号 / 任务 / Done 条件）
3. **所需技术栈**：语言版本（精确到 `>=3.11,<3.12`）/ 框架 / 存储 / 关键依赖 / 运行配置
4. **代码做法**：每个文件现状（占位→要做的）+ 实现要点 + 测试要求
5. **接入骨架**：抽象方法 / 接口契约（附代码示意）
6. **边界与红线**：不越界规则 + 违反=返工的铁律（成功码/错误码/确定性校验/降级/幂等/脱敏）
7. **验收标准**：可勾选 Done 清单 + 参考文档索引

## 配套产出（同样要写文件）

- **数据缺口清单**：功能所需字段 vs 现有表结构逐项比对（✅/⚠️/❌）——**实测 DDL**（`grep CREATE TABLE sql/*.sql` + `sed -n '/CREATE TABLE.../,/ENGINE/p'`），不能只看文档描述；统计"能完整实现几条/部分几条/严重缺口几条"
- **对齐提案**：每条待拍板事项带"建议默认值 + 不采纳后果"（架构组只需说同意/改）；按优先级分组（P0 不拍板无法开工 / P1 影响质量 / P2 口径确认）

## 关键纪律（血泪教训）

1. **参数必须读全源文档，禁止基于截断输出/记忆推断**——本 skill 首战教训：20 条规则任务书有 3 处参数写错（RW-010/012/015），因为源文件被 read_file 截断（`... [truncated] ...`）没继续读，凭印象补全了错误阈值。**遇到 truncated 提示必须继续读，再提炼表格**。
2. **权威源优先级写清楚**：冻结契约 > 需求文档 > 摘要/纪要文档；冲突时在文档里标注差异点（编号/语义/阈值/权限归属），交给架构组拍板，不要自己悄悄选一边。
3. **分工信息以最新文档为准**：README / AGENTS.md / 职责矩阵是权威；启动会纪要多半过时（本次出现"谁负责风控+操作"两种说法）。先对比再写，冲突要提醒用户确认。
4. **给 agent 的文档要"零歧义"**：所有契约值（错误码、阈值、表字段）直接内嵌，不让 agent 再去找源文件；但来源路径仍要列在索引里供核对。
5. 文档产出后主动指出"需要与架构组确认的 N 件事"，让用户带清单去开会。

## 验证

- [ ] 每份任务书有 7 要素完整
- [ ] 参数表与源文档逐条核对过（尤其源文件被截断过的部分）
- [ ] 边界/红线明确列出禁止项
- [ ] 待确认事项编号清晰、带建议默认值
